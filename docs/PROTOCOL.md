# OpenBridge BLE & E2EE Protocol Specification (v1)

## 1. BLE GATT Profile

- **Peripheral (GATT Server):** Android device
- **Central (GATT Client):** iOS device (supports `UIBackgroundModes: bluetooth-central` and `CBCentralManagerOptionRestoreIdentifierKey`)
- **Primary Service UUID:** `7F5B0001-9A3C-4E1D-8B2A-1C4D5E6F7A01`
  - **RX Characteristic (iOS -> Android):** `7F5B0002-9A3C-4E1D-8B2A-1C4D5E6F7A01`
    - Properties: `Write`, `Write Without Response`
  - **TX Characteristic (Android -> iOS):** `7F5B0003-9A3C-4E1D-8B2A-1C4D5E6F7A01`
    - Properties: `Notify`, `Read`
    - Descriptor: CCCD (`00002902-0000-1000-8000-00805F9B34FB`)

## 2. Transport Framing

Because BLE characteristics split writes/notifications according to the negotiated MTU (20–512 bytes), every message is framed in a stream buffer:

```text
+--------+--------+--------+--------+----------------------+
|  0x4F  |  0x42  | len_hi | len_lo | UTF-8 JSON Payload   |
|  ('O') |  ('B') | (uint8)| (uint8)| (len bytes, max 64K) |
+--------+--------+--------+--------+----------------------+
```

- `len = (len_hi << 8) | len_lo`
- Senders chunk the complete `[header + payload]` byte sequence into chunks of `max(20, mtu - 3)` bytes.
- Receivers append incoming chunks into a byte buffer and extract complete frames whenever `buffer.size >= 4 + len`.

## 3. Pairing & End-to-End Encryption (E2EE)

- **Key Exchange:** ECDH on NIST **P-256 (`secp256r1`)**
- **Key Format:** X9.63 uncompressed public key (65 bytes: `0x04 || X(32) || Y(32)`), Base64 encoded.
- **Key Derivation:** HKDF-SHA256
  - `IKM`: 32-byte raw ECDH shared secret
  - `Salt`: UTF-8 `"OpenBridge-v1"`
  - `Info`: UTF-8 `"session-aes-256-gcm"`
  - `Length`: 32 bytes (AES-256 key)
- **Cipher:** AES-256-GCM with 12-byte random nonce per message and 16-byte authentication tag.

### QR Code Payload (Generated by Android)
```json
{
  "v": 1,
  "id": "android-device-uuid",
  "name": "Pixel / Galaxy",
  "pub": "<base64-65-byte-p256-pub>",
  "svc": "7F5B0001-9A3C-4E1D-8B2A-1C4D5E6F7A01"
}
```

### Pairing Handshake
1. iPhone scans QR code, stores Android `deviceId`, `name`, and `androidPubKey`.
2. iPhone generates its own P-256 keypair and derives `sharedKey = HKDF(ECDH(iphonePriv, androidPub))`.
3. iPhone connects over BLE, subscribes to `TX`, and writes an unencrypted `PAIR_HELLO` to `RX`:
   ```json
   {
     "type": "PAIR_HELLO",
     "v": 1,
     "deviceId": "iphone-uuid",
     "deviceName": "iPhone",
     "pub": "<base64-65-byte-p256-pub>"
   }
   ```
4. Android computes `sharedKey = HKDF(ECDH(androidPriv, iphonePub))` and responds with an **encrypted** `PAIR_ACK`.
5. Once verified, all subsequent messages MUST use the encrypted envelope:
   ```json
   {
     "e": 1,
     "n": "<base64-12-byte-nonce>",
     "c": "<base64-ciphertext-plus-16-byte-tag>"
   }
   ```

### `PAIR_ACK` (Android -> iOS)
```json
{"type":"PAIR_ACK","deviceName":"Galaxy","ts":1732480000000}
```

### `PING` / `PONG` (Bidirectional)
```json
{"type":"PING","ts":1732480000000}
{"type":"PONG","ts":1732480000000}
```


## 5. Local Wi-Fi Audio Stream (Optional Port 54810)
- Transport: TCP stream on Android's Hotspot / local Wi-Fi IP (`wifiIp:54810`).
- Format: Raw 16-bit signed little-endian PCM, 16,000 Hz, mono (`32,000 bytes/sec`).
- Both endpoints read and write full-duplex PCM frames once a call is answered (`ACCEPT` / `OFFHOOK`).
